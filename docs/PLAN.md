# План портирования Uzebox на Karabas Go / Mini / Mini G

Статус: 2026-11-19, варианты выбраны (A + V1 + M2 + L1, раздел 4), Ф0 закрыта (ядро AVR == uzem), Ф1 собрана для Mini G, ждёт проверки на плате. Работа идёт по фазам
раздела 5 (одна ветка на фазу, один PR в конце).

## 1. Что такое Uzebox (исходные данные)

- Консоль из одного ATmega644 (64 КБ flash, 4 КБ SRAM, 2 КБ EEPROM) на **28.63636 МГц** (8 × NTSC burst) +
  AD725 RGB→NTSC. Кадрового буфера нет: картинку рисует программа, выводя пиксели в PORTC
  (цвет 3:3:2) с точностью до такта; синхро — PB0, строка = **1820 тактов** (15.734 кГц), 262 строки без чересстрочки, 60.05 Гц.
- Звук: 5 каналов, микшируются программно раз в строку, выход — ШИМ таймера 2 (OCR2A), ~15.7 кГц, 8 бит.
- Ввод: два SNES-джойстика (сдвиговые регистры на PORTA), SNES-мышь, PS/2 клавиатура через адаптер на порту 2.
- Периферия: SD по SPI (FAT, Bootloader5 прошивает игру `.uze` в flash через SPM), SPI RAM 23LC1024 (128 КБ),
  UART0 → ESP8266 (Uzenet), MIDI IN.
- Готовой FPGA-реализации Uzebox нет (поиск 2026-11-19). Эталон поведения — эмулятор `upstream/uzebox/tools/uzem`
  (`avr8.cpp`, потактовый). Игры и тесты — `upstream/uzebox/demos`. Подробно: заметка `reference-uzebox-upstream`.

## 2. Что дают платы

Все три платы (XC6SLX25, ISE 14.7): 2 МБ SRAM (MA/MD), SDRAM, SD-карта на выводах ПЛИС (`SD_*`), ESP8266 на UART
(`UART_RX/TX/CTS`), MCU-линк v2 (OSD, USB-клавиатура/мышь/джойстики, загрузка файлов), I2S-ЦАП, HDMI (Mini, Mini G) /
VGA (Go). MIDI только на выход — MIDI IN Uzebox не переносим.

Хорошее совпадение: строка Uzebox × 2 = **31.47 кГц — ровно строчная частота VGA 640×480**; кадр 524 строки,
60.05 Гц (у VGA 525 и 59.94 — мониторы принимают).
Значит, простой удвоитель строк даёт стандартную развёртку без кадрового буфера.

## 3. Варианты (нужен выбор)

### 3.1 Процессор AVR (главное решение)

| | Вариант | Плюсы | Минусы |
|---|---|---|---|
| **A** | **Своё ядро ATmega644** (Verilog-2001 под XST), потактово как в даташите; uzem — оракул (сравнение трасс PC / такт / запись в порт) | полный контроль над таймингом прерываний и таймеров (на этом стоит весь Uzebox); всё под GPL-3; AVR прост (~130 команд) | больше работы на старте (оценка: ядро ~2 недели вечеров до прохождения unittest) |
| B | Взять **cmstar0/atmega-xmega-soft-core** (GPL-2+, потактовый, проверен на Arduboy_MiSTer) | ядро уже проверено играми | под Altera (`lpm_mux` в таймерах), XST-совместимость неизвестна; периферию ATmega644 (timer1 CTC, timer2 PWM, SPI, UART0, SPM) всё равно писать/править; чужой код отлаживать |
| C | softavrcore (LGPL) / nanamake avr_cpu | малы | **не потактовые** — для Uzebox не годятся |

**Рекомендую A**, с uzem как эталоном; из B можно подсматривать решения, но не копировать.

### 3.2 Видео

| | Вариант | Суть |
|---|---|---|
| **V1** | **Удвоитель строк 1:1 по тактам** | PORTC пишется в строчный буфер на каждом такте CPU (1820 байт = 1 BRAM), выводится дважды на 57.27 МГц (2× CPU): 1440×480 активных, 31.47 кГц, 60.05 Гц. Без кадрового буфера, задержка полстроки, все видеорежимы (4…8 тактов на пиксель) без искажений. HDMI как CEA 1440×480p (VIC 14/15 близок по частотам строк/кадров), VGA на Go |
| V2 | Кадровый буфер в SRAM | вывод стандартным 720×480p@27 МГц / 640×480; масштабирование, лишний кадр задержки, разрывы |
| V3 | Удвоитель с выборкой каждые 2 такта | 720 пикселей, но режимы с 5 тактами на пиксель дают неравные пиксели |

**Рекомендую V1.** Проверить на телевизоре/мониторе пользователя; запасной путь — V2.

### 3.3 Программная память и загрузка игр

| | Вариант | Суть |
|---|---|---|
| **M1** | **flash 64 КБ в BRAM** (32 из 52 RAMB16) | выборка за такт, LPM/SPM просто; SRAM 4 КБ и EEPROM 2 КБ тоже в BRAM |
| M2 | flash во внешней SRAM | экономит BRAM; 10 нс SRAM на 28.6 МГц успевает, но делить шину с SPI RAM и загрузчиком |
| **L1** | **Игра `.uze` через OSD** (элемент `FL`, MCU читает файл с SD и шлёт в ядро) | ядро пропускает 512-байтный заголовок, пишет в flash, сбрасывает AVR. Быстрый старт, SD ядру не нужна |
| L2 | **Родной Bootloader5** | меню Uzebox на SD; нужны SPI SD на выводах ПЛИС, SPM, секция загрузчика. Аутентично, нужно и для игр, читающих SD (Uzeamp и др.) |

**Рекомендовал M1 + L1 в Ф1, L2 — в Ф2; выбрано M2 + L1** (раздел 4) (обе остаются: OSD-загрузка и Bootloader5).

### 3.4 Остальная периферия (решение по умолчанию, можно поправить)

- Джойстики: USB-джойстики MCU-линка → модель двух SNES-контроллеров на PORTA (клавиатура как джойстик 1).
- Звук: берём значение OCR2A напрямую (без ШИМ) → 16 бит в HDMI / I2S; простой ФНЧ как RC на плате Uzebox.
- SPI RAM 23LC1024 → в SDRAM платы (SRAM занята выборкой команд каждый такт, см. M2). EEPROM — в BRAM, сохранение на SD — позже.
- UART0 → ESP8266 платы (Uzenet работает «как есть», если прошивка ESP совместима).
- SNES-мышь, PS/2-клавиатура (из USB-клавиатуры) — в Ф4.

## 4. Принятые решения

Выбор пользователя 2026-11-19: **A + V1 + M2 + L1**.

- **A — своё ядро ATmega644**, потактово по даташиту и AVR Instruction Set Manual, Verilog-2001 под XST.
  Эталон — uzem (`tools/uzem/avr8.cpp`, GPL-3), сравнение трасс. Чужие AVR-ядра только для справки.
- **V1 — удвоитель строк 1:1 по тактам**, вывод 1440×480 на 57.27 МГц (почему так — ниже).
- **M2 — flash 64 КБ во внешней SRAM платы** (на всех трёх платах 2M×16, 21 бит адреса: слово команды AVR —
  одно обращение). Выборка команды каждый такт CPU (34.9 нс): адрес из регистра IOB, SRAM 10 нс + выводы —
  около 20 нс, запас есть; это проверить по trce в Ф0/Ф1. LPM/SPM читают/пишут SRAM в тактах, когда
  CPU стоит (LPM 3 такта, SPM), загрузчик пишет, пока AVR в сбросе. SRAM 4 КБ и EEPROM 2 КБ — в BRAM.
  Если по таймингу не выйдет — откат на M1 (flash в BRAM, 32 RAMB16).
- **L1 — игра `.uze` через OSD** (`FL`), Bootloader5 — в Ф2.

### Почему 1440×480

- **Горизонталь, 1440.** Uzebox не имеет «пикселей» в железе: картинка — это значение PORTC, меняющееся на
  каком-то такте CPU. Разные видеорежимы держат пиксель разное целое число тактов: режим 1 — 40 тайлов × 6 точек
  = 240 точек по 6 тактов, режим 9 — 60 × 6 = 360 точек по 4 такта; оба дают **1440 тактов** видимой части
  строки, это ширина экрана Uzebox (узкие режимы вроде 3 и 13 — меньше). Если выводить **одну точку HDMI на
  такт CPU**, любой режим (4, 5, 6, 7 тактов на точку) воспроизводится точно, без пересчёта и без знания режима.
  При 720 точках (через такт) режимы с нечётным числом тактов на точку дают точки разной ширины (вариант V3).
- **Частота 57.27 МГц.** Удвоитель показывает каждую строку дважды за время одной исходной, значит выводит
  в 2 раза быстрее: 2 × 28.636 = 57.27 МГц, 1820 точек на строку → 31.78 мкс = строка VGA (31.47 кГц).
  Это та же частота CPU × 2 из одного PLL, поэтому строчный буфер работает без асинхронных переходов.
- **Вертикаль, 480.** Uzebox рисует 224 строки (28 тайлов × 8) из 262; удвоение → 448 видимых строк
  внутри окна 480 (+ поля), всего 524 строки = 60.05 Гц.
- **Почему это примет телевизор.** 1440×480p — стандартный режим CEA-861 (VIC 14/15: 720×480p с двойным
  повтором точки, 54 МГц, 1716 точек в строке). Частоты строк и кадров у нас те же, отличается только
  число точек в строке (1820 против 1716) и тактовая (57.27 против 54 МГц). Приёмник объявляем 1440×480,
  он масштабирует в 4:3 — тот же формат, под который рисовались игры для NTSC-телевизора.
  Риск: строгие HDMI-приёмники; проверяем на плате в Ф1, запасной путь — V2.
- **Подвох для Ф1.** Во время кадрового синхроимпульса kernel выдаёт на PB0 уравнивающие импульсы двойной
  частоты, поэтому удвоитель берёт начало строки не по каждому фронту PB0, а по своему счётчику 1820,
  подстраиваясь по синхро вне VSYNC.

## 5. Фазы

- [x] **Ф0. Ядро AVR в симуляции** (ветка `f0-avr-core`, слита в master 2026-11-19). Сделано:
  - `src/rtl/avr/avr_core.v` — своё ядро AVR (ATmega644, все команды AVR5 кроме SPM — он пока 4-тактовый NOP, Ф2),
    `avr_io_m644.v` — IO (порты, timer 1, watchdog, EEPROM, OCR2A = звук, остальное — регистры), `atmega644.v` —
    ядро + IO + SRAM 4 КБ в BRAM; программная память снаружи (M2).
  - Проверка — **синхронный прогон с uzem** (`src/sim/lockstep`): модель Verilator и `avr8.cpp` из upstream в одной
    программе, после каждой команды сравниваются PC, число тактов, r0–r31, SREG, SP, пиксель PORTC, timer 1, TIFR1,
    WDTCSR, порты, все прочие регистры IO, SRAM — каждые 4096 команд. Кадры RTL — в PNG (окно как в uzem).
    `src/sim/build_uze.sh` собирает uzem, утилиты и игры в копии (upstream не трогается),
    `src/sim/lockstep/run_lockstep.sh <игра> -n кадров -p png`, `run_suite.sh [кадров]` — весь набор.
  - Синтез одного `atmega644` (`src/synth/synth_core.sh`, XST + map + par): 3701 LUT, 646 FF, 3 RAMB16, 1 DSP48;
    Fmax после разводки 47.4 МГц (нужно 28.64). LUT можно сократить (регистровый файл на LUTRAM, общие сумматоры) —
    если понадобится в Ф1.
  - Где uzem отличается от ATmega644 и как это учтено (стенд правит оракул, RTL — как железо):
    EEPROM — uzem добавляет 4 такта, не двигая таймер; ATmega644 стоит 4 (чтение) / 2 (запись) такта при идущих
    таймерах — стенд прогоняет эти такты через `update_hardware()`. PORTB, PORTC, OCR2A uzem в `io[]` не хранит —
    не сравниваются (PORTC — через пиксель). Watchdog uzem случаен (`rand()`), стенд подменяет `rand()` на 0.
  - Поведение uzem, принятое в RTL (на нём проверены игры): вход в прерывание 3 такта; после SEI / записи I в SREG
    прерывание откладывается на две команды; флаги timer 1 появляются в TIFR1 через такт после события; запись
    OCR1x видна сравнению в том же такте; timer 1 считает каждый такт при любом CS1x; приоритет векторов —
    по даташиту (WDT > COMPA > COMPB > OVF).
  - Для Ф1: видимое окно — 1440 тактов с 168-го после фронта PB0, 224 строки с 38-й после полустрок кадрового
    синхроимпульса; цвет — биты 0–2 R, 3–5 G, 6–7 B.
  - Результат 2026-11-19: `run_suite.sh 300` — 12 игр (unittest, Megatris, SpriteDemo, DonkeyKong, Mode5Demo,
    Mode9Demo, Mode13ExtendedDemo, SpaceInvaders, PacMan, ControllerTester, MusicDemo, Arkanoid `.uze`) по 300
    кадров, ~1 млрд команд: **RTL == uzem** по каждому такту. Найдена и исправлена ошибка RTL: вектор прерывания
    читался после сброса флага (защёлкивается в первом такте входа). Режимы 1, 3, 5, 9, 13 kernel покрыты.
  - Ввод: `-a` (`AUTOPLAY=1 run_suite.sh`) — раз в 20 кадров случайная кнопка SNES пада 1 держится 5 кадров, потом
    всё отпущено (игры ждут отпускания: `while(ReadJoypad(0)!=0)`). Megatris с `-a`: 600 кадров, меню → игра,
    164 млн команд, RTL == uzem. Полный набор гонять после изменений CPU / IO, для прочего хватает одной игры.
  - uzem не видит подключённый пад (линия данных в покое = 1), поэтому ControllerTester пишет «NO CONTROLLER» — это
    свойство эталона; модель SNES-пада для платы — Ф1.

## 6. Открытые вопросы

- Как ядро и MCU делят SD-карту (Ф2)? Посмотреть, как это сделано в tsconf / nanomig.
- Принимают ли HDMI-приёмники 1440×480 на 57.27 МГц (не ровно 54 МГц CEA)? Проверить на Ф1; запас — V2.
- Нужен ли режим «пауза / сохранение состояния» в OSD.
- OSD на 1440 × 480: `kg_l2_osd_overlay` берёт масштаб 2 по обеим осям, а точки вдвое уже, чем высота —
  меню вдвое уже нормального. Исправление — горизонтальный масштаб в modules (отдельный PR там), если мешает.
- Звук без фильтра (ступеньки 15.7 кГц): на оригинале — RC-фильтр после ШИМ; добавить ФНЧ, если слышно.
- Публичный ли репозиторий (upstream GPL-3 — ядро тоже GPL-3).
